# Спецификация 14 — надёжность интеграции с Shikimori: лимиты и свежие постеры

Статус: согласовано с владельцем продукта (2026-07-30). Реализовано в фазе 14.

Обе проблемы найдены на живом сценарии «собрать пикер по спискам трёх
пользователей» (обход 135 аниме): агентские сценарии делают сотни запросов и
импортируют десятки постеров.

## Проблема 1 — минутный лимит Shikimori

Клиент держал только паузу 250 мс (≈4 rps) и повторял 429 через 1 с / 2 с. Но у
Shikimori **два** лимита: 5 запросов/сек **и 90 запросов/минуту**. Обход
списка (роли каждого аниме) упирался в минутный лимит примерно на 90-м запросе,
а секундного бэкоффа не хватало — окно минутное, и сценарий падал с
`RATE_LIMITED`.

**Решение.** Чистая политика в `src/lib/domain/rate-limit.ts`:

- `nextDelayMs(history, now, cfg)` — задержка перед следующим запросом с учётом
  обоих ограничений: пауза после предыдущего запроса и **скользящее окно**
  (когда окно заполнено — ждать, пока из него выпадет самый старый запрос).
- `trimHistory` — выбрасывает метки времени вне окна.
- `retryDelayMs(attempt, schedule, retryAfter)` — пауза перед повтором 429:
  `Retry-After` сервера приоритетнее (если значение осмысленное, ≤120 с), иначе
  расписание; `null` = бюджет исчерпан.

Конфигурация в `src/lib/shikimori.ts`: API — 250 мс между запросами и **80
запросов в минуту** (запас к лимиту 90), расписание повторов 2 с / 8 с / 20 с.
Картинки (`/system`, `/uploads`) в минутный бюджет API не входят — для них
только пауза 250 мс. Тестовый хук `SHIKIMORI_RETRY_MS="10,20"` укорачивает
расписание, чтобы сьют не ждал секунды.

## Проблема 2 — постер из импорта не совпадал с сайтом

REST v1 отдаёт `image.original` вида `/system/animes/original/16498.jpg?…` —
это **старая уменьшенная копия**. Сайт же показывает постер из
`/uploads/poster/<animes|characters>/<id>/<hash>.jpeg` (GraphQL
`poster.originalUrl`). Замеры: «Атака титанов» — legacy 225×350 / 57 КБ против
685×975 / 371 КБ на сайте; у персонажа Харухи размер тот же, но **файл другой**
(40753 против 41574 байт) — то есть legacy-путь отдаёт устаревшую ревизию арта.

**Решение.** Импорт берёт постер как на сайте:

- `isSafePosterUrl(base, url)` (домен) — SSRF-гард для абсолютного URL: тот же
  origin, что у настроенной базы, путь строго
  `/uploads/poster/(animes|characters)/<id>/<файл>.(jpg|jpeg|png|webp)`.
- `fetchGraphql` + `fetchFreshPosterUrls(type, ids)` — пакетный запрос
  `poster.originalUrl` (один запрос на список id).
- `importPoster` сначала пробует свежий URL (свой, если передан в
  `posterUrl`, иначе резолвит сам), а при отсутствии/ошибке/чужом хосте
  **откатывается на legacy `/system`** — старое поведение сохраняется как
  фолбэк, ошибок у пользователя не появляется.

Публичный контракт MCP-инструментов не меняется: `import_shikimori_poster` и
`add_tile_from_shikimori` автоматически получают свежий постер по `type` + `id`.

## Проверка

- Юнит: `rate-limit.test.ts` (первый запрос без задержки, пауза, ожидание
  освобождения окна, устаревшие метки не считаются, максимум из двух ожиданий,
  расписание повторов и `Retry-After`), `shikimori.test.ts` — `isSafePosterUrl`
  (чужой хост, другой протокол/порт, не-poster путь, traversal, не-абсолютный).
- Интеграция: локальный стенд с `/api/graphql` и `/uploads/poster/...` —
  импорт берёт свежие байты (не legacy), заранее переданный `posterUrl`
  используется без лишнего GraphQL-запроса, три фолбэка (постера нет, GraphQL
  500, чужой хост) приводят к legacy-копии; ретрай 429 и явная ошибка после
  исчерпания бюджета.
- Живьём: `fetchFreshPosterUrls` на реальном API + импорт «Атака титанов»
  (685×975, 371 КБ вместо 225×350) и персонажа (актуальная ревизия файла);
  обход 135 аниме без падений по лимиту.
